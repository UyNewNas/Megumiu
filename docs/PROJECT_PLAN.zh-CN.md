# Megumiu 项目计划书

日期：2026-10-07
仓库：[UyNewNas/Megumiu](https://github.com/UyNewNas/Megumiu)
当前阶段：第一阶段，采集与测量基础建设；三相机硬件验收待完成。

Megumiu 希望通过三台相机，在不佩戴身体绑带的情况下重建人体运动，并将追踪数据交给 SteamVR。首个可交付目标是单人、固定室内活动区，保留头显和手柄追踪，由视觉补齐腰和双脚。在真实 VR 负载下，动作发生至 SteamVR 接收姿态的延迟以 P95＜100ms 为验收目标；50–80ms 是优化方向，10–20ms 是后续探索目标，均不是已经验证的性能。

## 立项依据与范围

[MocapForAll 官方产品说明](https://vrlab.akiya-souken.co.jp/en/products/mocapforall/)展示了两台以上摄像头通过 Virtual Motion Tracker 接入 SteamVR 的先例，同时说明其延迟高于常规 VR 设备。这证明了路线具备实践基础，不能证明 Megumiu 已达到目标。项目价值在于延迟、抖动、遮挡恢复及配置体验。

首版输出腰、左脚、右脚的位置与旋转。位置正确不代表脚尖朝向正确，选用模型时必须考虑脚跟、脚尖等信息。膝、胸、肘等额外追踪点在腰脚稳定后扩展。多人、移动机位、所有服装和姿态下的可靠追踪暂不列入首版验收。目标游戏需要支持全身追踪；SteamVR 接入本身不保证所有游戏可用。

## 技术路线

三路图像与时间信息 → 2D 人体和脚部关键点 → 多视角三角化 → 骨长与关节约束 → 低延迟滤波 → SteamVR 虚拟追踪器。

优先评估 [RTMPose 官方项目](https://github.com/open-mmlab/mmpose/tree/main/projects/rtmpose)中包含所需脚部关键点的模型，按实际硬件比较精度与处理耗时。其公开基准只用于选择候选模型，不能直接充当三相机与 VR 同时运行的端到端基准。初期考虑复用 Virtual Motion Tracker；有明确需求后再评估自有驱动，[Valve 的多追踪器示例](https://github.com/ValveSoftware/openvr/blob/master/samples/drivers/drivers/simpletrackers/README.md)可作接口参考。

相机之间、地面和 SteamVR 坐标系需统一标定。正常三角化要求同一关节点在至少两个视角中有可靠观测；全部遮挡时只能短暂预测或报告无效状态，不能把推测当成测量。相机移动、变焦或对焦变化可能影响标定，应检查并按需重做。

## 延迟和精度口径

分别记录以下量，不混用名称：

| 指标 | 起点与终点 | 可以说明什么 |
| --- | --- | --- |
| 读取耗时 | 开始读取至读取返回，使用同一单调时钟 | 读取阻塞和后端处理耗时 |
| 到达时间差 | 多路图像读取返回的主机时间差 | 软件接收行为，不是曝光同步误差 |
| 曝光时间差 | 同一物理事件在各路曝光中的相对时间 | 多视角采样是否对应同一时刻 |
| 追踪延迟 | 物理动作发生至 SteamVR 接收对应姿态 | 项目 P95＜100ms 的最终验收量 |
| 显示延迟 | 物理动作发生至头显显示对应变化 | 另外包含游戏、合成与显示链路 |

30、60、120 FPS 的帧间隔分别约为 33.3、16.7、8.3ms；曝光、传输、计算和排队还会增加延迟。[MocapForAll 相机说明](https://akiya-research-institute.github.io/MocapForAll-Manual/en/how-to-capture/get-cameras/)也强调传输与同时运行 VR 的影响。软件在读取返回后打时间戳，无法知道此前图像已在相机或驱动中等待多久。

验收报告同时给出样本数、P50、P95、最大值、失败与缺失比例及测试条件。位置误差、朝向误差、静止抖动、脚滑和遮挡恢复时间需分别测量。第一阶段确定硬件与参考测量能力，第二阶段在基线结果上冻结精度门槛，不能以未知硬件承诺厘米级精度。

## 阶段与验收

| 阶段 | 交付物 | 通过与退出条件 |
| --- | --- | --- |
| 一 采集与测量 | 三路采集工具、配置、逐帧时间日志、报告、硬件测试指南、可重复模拟输入 | 软件测试通过；硬件同时连续采集至少 10 分钟，无意外断流，报告实际交付帧率和长间隔；完成共同光学事件测量，明确同步偏差、测量误差及采集延迟预算。硬件不足或物理测量缺失时，只能交付工具，不能宣告硬件验收通过 |
| 二 姿态重建 | 相机标定、三维骨架、腰脚位置与朝向、录像回放基线 | 在固定动作集完成误差与失效统计，坐标及左右身份正确；冻结后续精度门槛。若同步、遮挡或标定主导误差，返回采集与机位设计，不先堆训练数据 |
| 三 VR 验证 | SteamVR 输出、空间标定、真实游戏负载报告 | 在约定动作集和硬件上，物理参考验证追踪延迟 P95＜100ms，同时满足已冻结的稳定性门槛。延迟通过而脚滑、抖动不可用，仍不通过 |
| 四 数据优化 | 失败样本集、标注规范、训练与独立测试集、版本对比 | 新版本在独立测试集提升目标场景，正常场景与延迟不出现不可接受退化。无明确收益则保留基线并停止该轮扩充 |

每阶段保存配置、代码版本、原始测量和结论。阶段一无需等模型训练即可开始；姿态算法可并行研究，但下一阶段的正式性能结论依赖前一阶段证据。

## 数据与主要风险

先用现成模型收集戴头显、背身、蹲坐、交叉腿、快动作和宽松衣服等失败案例，再做自动预标注与人工修正。标注应含脚部细节、左右身份、遮挡状态及不确定性。训练和测试按人物、场次或房间划分，避免相邻帧泄漏。参考设备可临时用于采集三维真值，最终运行仍无需绑带。

标注不能修复相机不同步、错误标定和所有视角均不可见的问题。全局快门能减少逐行曝光造成的运动形变，但不等于多相机触发同步，二者需分别核实。[Basler 快门说明](https://docs.baslerweb.com/electronic-shutter-types)

主要工程风险是 USB 带宽和隐藏缓冲、自动曝光造成降帧、GPU 与游戏争用、遮挡和朝向不确定、滤波引入滞后。对应策略是先测采集、保留最新帧并统计丢弃、显式报告失效、以物理参考检查延迟，并将困难场景纳入固定回归集。

## 代码与交付方式

代码、计划、测试和 GitHub Actions 集中在本仓库。CI 负责软件测试、模拟输入回归和构建；发布流程生成版本化软件包及校验信息。安装包、依赖与模型许可证在纳入发布前逐项确认，硬件测试资料与人体视频默认不随源码公开。

CI 通过仅证明对应软件检查通过。三相机、GPU、头显与游戏的实际表现由硬件报告证明。硬件型号、预算和可投入时间尚未确定，暂不编造采购金额与工期；先依据[第一阶段硬件验收指南](HARDWARE_VALIDATION.zh-CN.md)建立可复现基线，再决定采购和后续投入。
